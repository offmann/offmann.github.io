An AI Platform for a Mid-Size Company: Pull, Not Push

Jottings - Feb 6, 2026

AI work is changing fast. Take the details here with a grain of salt. Implementation is getting cheaper, so bottlenecks move. I am trying to focus on principles and reusable primitives more than on any specific tool.

When I say “AI platform” I do not mean a unified UI where you do everything. I mean an operating model plus paved roads: shared components, stable interfaces, and guardrails that let teams ship quickly with flexibility.

TLDR

I think an AI platform is not a tool you buy or a framework you mandate. In my opinion it is how you help teams ship AI powered product features faster, safer, and cheaper.

Start from bottlenecks, not tools:

  • Alignment: what to build, why now, what good means
  • Context: governed, correct, fresh data the model can safely use
  • Evaluation: how you move from demo to measurable quality
  • Operations: tracing, debugging, incident response, cost control, governance

Scope: AI in the product

People use “AI platform” for two different things. One is building AI powered software where the model is part of the product. The other is using AI for coding. This article is about the first one.

Aside: using AI for coding

I think agentic coding is real and it changes delivery speed. But most teams do not build a platform for it. They adopt tools like Cursor, Codex, or Claude Code, then rely on normal engineering controls like reviews, tests, and security scanning.

That is a separate topic with its own details. I only mention it because it is one more reason mandates age badly.

Pull, not push

I think most AI platform efforts fail because they start with a tool and then push it on teams. In my opinion the better posture is to stay tool agnostic and pull based. Teams should adopt because the paved road is the easiest safe path.

That usually means: fast onboarding, safe defaults, clear runbooks, templates, and real support. If the platform creates friction, teams will route around it.

Start from bottlenecks

I like to map the real workflow: idea, experiment, MVP, production candidate, production. In mid to big companies, the model API call is rarely the hard part. The MVP to production cliff is.

1) Alignment

Alignment is agreeing on the user problem, success metrics, risk, and what “done” means. Without this, teams optimize demos and argue late. A platform can help with decision templates, quality checklists, and a clear approval path for higher risk use cases.

2) Context

I think context engineering matters more than prompt engineering. Quality often comes from governed inputs: entity data, documents, features, timestamps, lineage, and permissions. If context is wrong you get bad outputs. If context leaks you get incidents.

3) Evaluation

It is easy to demo an MVP. It is hard to ship a reliable feature. In my opinion teams need a way to answer: is this version better, where does it fail, and what is the risk of shipping it?

4) Operations

LLM Ops is still Ops. You need tracing, monitoring, and incident response. The difference is that AI failures can look healthy at the infrastructure level. A 200 response can still be wrong, unsafe, or too expensive.

Compounding primitives

I think a good platform invests in primitives that many teams can reuse, while keeping tool choice flexible:

  • Context contracts: stable APIs and data packages that are safe by default
  • Evaluation building blocks: datasets, regression runs, and release gates
  • Tracing and auditability: enough visibility to debug and explain behavior
  • Model access control: routing, budgets, rate limits, and permissions

In my opinion the interface and the discipline are the product. The internal implementation can change.

Context is the moat

In my opinion models are becoming easier to access, so they are rarely the durable advantage. What compounds is domain context, integration into real workflows, evaluation discipline, and operating discipline.

Example: context packages in an affiliate network

In an affiliate network like Awin, a “publisher snapshot” context package can bundle facts, performance features, relevant documents, freshness, and permissions. Many AI features can reuse that same governed input, even if the prompts and evaluations are feature specific.

Optional: an embedding factory

If overlap is real, a shared embedding and vectorization factory can be high ROI. I would not build it unless multiple teams reuse it. Production needs versioning, refresh SLAs, access control, and traceability.

Evaluation and release discipline

I think vibe testing is the default failure mode. The minimum system is simple:

  • Define quality explicitly: correct, unacceptable, and “good enough”
  • Use real examples early: synthetic data can help you start, but it misses real edge cases
  • Run regressions: prompt changes, retrieval changes, tool changes, model upgrades
  • Human review where needed: subjective outputs need humans in the loop
  • Release gates and rollbacks: block releases below thresholds and roll back quickly

In my opinion a platform wins when this is easy and normal.

What to standardize, and what not to standardize

I think you should standardize the parts that repeat and reduce risk:

  • context access and permissions
  • evaluation building blocks and release gates
  • tracing, audit, and incident response basics
  • governance boundaries and cost controls

I do not think you should standardize one model, one vendor, or one agent framework. Those choices change too fast.

Common failure modes

  • Starting with a tool instead of a bottleneck
  • Building too much before proving reuse
  • Forcing adoption and creating quiet workarounds
  • Shipping MVPs without evaluation and calling it done
  • Ignoring cost until it spikes
  • Adding capabilities before guardrails and auditability

Closing opinion

I think a good AI platform is boring in the best way. It is focused on discipline and compounding reuse. It lets teams move fast without breaking trust.

If you remember one thing, make it this: start from bottlenecks, invest in compounding primitives, and keep the platform pull based.
